# Agent API — corrections FIRST, vendor docs second

> ⚠️ **Read this page before any ServiceNow write via the sn-scriptsync agent API.**
> `agentinstructions.md` and the `agentrules/skills/snu-*` docs are **regenerated by the
> extension on every start** — they are vendor-owned, cannot be patched, and omit or
> contradict the corrections below. **Where they disagree with this page, THIS PAGE
> WINS.** (At last verification the vendor docs omitted the dual-switch rule entirely
> and taught `scope` as a name string.)

## The corrections

Each of these is a silent-failure mode observed in real engagements: the API reports
success while the platform does something else. Items flagged *(verify on your instance
first)* were confirmed on a specific instance/version — re-verify before relying on them.

1. **Dual `switch_context` before ANY scoped write — both calls, in order:**
   ```json
   { "command": "switch_context", "params": { "switchType": "updateset",   "value": "<update_set_sys_id>" } }
   { "command": "switch_context", "params": { "switchType": "application", "value": "<scope_sys_id>" } }
   ```
   Skipping the application switch makes `update_record`/`create_artifact` **silently
   no-op**: API returns `"success": true`, record unchanged, `sys_updated_on` frozen.
   The `scope` request parameter is NOT a substitute. The vendor §Transaction Scope
   section describes the URL mechanics but **omits this requirement** — do not trust it.

2. **`create_artifact` `scope` = the scope's `sys_id`, never the abbreviation.**
   Vendor examples (`"scope": "global"`, `"x_myapp"`) are wrong: a name string corrupts
   the `sys_scope` FK and breaks downstream cross-scope writes *(verify on your instance
   first)*. Literal `"global"` is acceptable only because it happens to BE a real
   sys_id. Look scope sys_ids up in [registry-sys-ids.md](registry-sys-ids.md).

3. **"success" ≠ captured. Verify BOTH after every write meant to ship:**
   - record: `query_records` → `sys_updated_on` moved, field holds the new value;
   - capture: `query_records` on `sys_update_xml` → row exists for the target with the
     RIGHT update set. UI/DB presence is not proof; only `sys_update_xml` is.
   (The PostToolUse capture-verifier hook that ships with this framework automates the
   second check — read its output after every write.)

4. **Journal fields:** `gr.work_notes = text` or `setJournalEntry` — **never
   `setValue('work_notes', …)`** (silently posts nothing). The one inversion of the
   "always setValue" convention. The vendor coding-standards doc teaches the
   unqualified rule — this exception overrides it.

5. **M2M relationship columns** (`sys_group_has_role.role`, `sys_user_grmember.user`, …):
   UPDATE is rejected but **Rhino doesn't throw** — script logs "success", data
   unchanged. Always DELETE + INSERT.

6. **Deletes:** show the list, get explicit user confirmation, THEN delete — including
   `run_background_script` deletes and any scoped Script Include delete helper (e.g. a
   `<YourScope>Util.deleteMultipleRecords`-style method), which bypass the API's delete
   gate.

7. **Reads can silently return empty:** wrong instance, cold helper tab, or invalid
   field names in the query give `count: 0` / unfiltered rows, NOT errors. Canary-read a
   known record before trusting absence; A/B-test filters.

8. **`run_background_script` is global-scope only AND does not inherit the update-set
   switch** — a `GlideUpdateManager2().saveRecord()` force-add via bg script lands in
   **Default** even after a "successful" `switch_context`. Programmatic force-add works
   ONLY with an explicit `GlideUpdateSet().set('<update_set_sys_id>')` in the script
   body *(verify on your instance first)*; alternatively use the classic list UI
   ("Actions on selected rows…" → Add to Update Set) in the tab whose set is active.
   Cross-scope deletes: refused — use a public scoped Script Include helper.
