not as a side effect of a story.

## Fact ownership — the drift killer

- **Single source per fact.** Every fact has exactly one owning page; everyone else links,
  never copies. A restated fact is a future contradiction.
- **Current-state claims live ONLY on process/registry pages.** Story pages never describe
  how things work now — they link to the owning process page (link even if the process
  page does not exist yet; planned targets are valid link targets).
- **sys_ids:** current sys_ids live ONLY in [registry-sys-ids.md](registry-sys-ids.md)
  (name, table, sys_id, owning story link, stamp). Story pages MAY inline sys_ids solely
  as *shipped-record history* (what was created then); readers resolve current values via
  the registry.
- **Gotcha ownership:** procedure-scoped gotcha → that skill's Gotchas section;
  platform-wide silent-failure class → [gotchas.md](gotchas.md). The other side links,
  never copies.

## Frontmatter per tier

All pages: `title:` plus `mentions:` — a list of sys_ids / artifact names / record names
the page references. The link checker harvests `mentions:` into the reverse index so
story-close can query "which pages reference the artifacts I touched".

| Tier | Required keys |
|---|---|
| Story | `story`, `title`, `tracker` (link to the backlog item in your work-tracking system), `status`, `updated-sets:` (list), `built:` (date range if known), `affects:` (processes/skills/decisions — story-close WALKS this list; explicit lists are the propagation mechanism), `mentions:` |
| Process / reference | `title`, `mentions:` |
| Registry | `title`, `verified:` (date of last verify-stamp), `mentions:` |
| Ledgers / index | `title` |

## Standing headers (exact text)

- **Story pages:**
  `> Immutable build record (wiki story tier). For CURRENT behavior always consult the process pages / live instance — never this page.`
- **Every non-registry, non-story page:**
  `> Verify sys_ids/states against the live instance before use.`
- **Registry pages:** no header — the `verified:` date stamp is the liveness signal.
  Verification is **on-touch** (story-close); there is no calendar sweep.

## Personas & Permissions — mandatory on every process page

Every `processes/` page carries a `## Personas & Permissions` section with **these four
subsections, in this order, with this exact wording**:

```markdown
### Who works this process
### What each persona may DO
### What each persona may SEE
### Where each rule is enforced
```

**Why this clause is not optional.** Everything else on a process page can, in principle,
be read off the instance. This section cannot, and it is the part a developer needs most —
"I have a story about cancelling a case; am I allowed to, and who else is?" A generated
brain that drops this clause reads as complete and is unusable, which is worse than one
that reads as thin. It was dropped once and the resulting deliverable mapped four personas
to landing pages and called it access documentation.

Three rules apply to the whole section, and they are checkable:

1. **Exclusions are content, not omissions.** `What each persona may DO` carries an explicit
   **May not** column with at least one non-empty cell. A denial that is merely absent is
   indistinguishable from a grant nobody got round to, and the difference is the whole
   question. Record deliberate denials so they are not "fixed" by mistake.
2. **Every permission claim names its enforcement point.** ACL, guard business rule, state
   flow, UI policy or dictionary — a claim about access with no enforcement point is a
   belief. Negative facts belong here too, and they are pure claim-ledger arithmetic:
   *"all 34 `sf_state_flow` rows leave `roles`, `manual_roles` and `automatic_roles` empty,
   so the dropdown offers every transition to everyone"* needed no human at all.
3. **An ungated path is stated as deliberate, or it is a TBD.** *"`canUserTransition`
   returns `true` unconditionally for this table; the write ACL is the gate"* is a finding.
   Silence is not.

**A persona is a named job, not a role bundle.** Groups and role grants are readable; which
of them constitute a persona is not, and the decisive human contribution is often
*subtractive* — "the `Test HSE selecteur` account is a leftover, not a fifth persona." Two
personas with identical roles are indistinguishable to every read there is.

**What each persona may SEE has a hard precondition.** Read ACLs never filter for an admin
session, so their *effect* is not demonstrable from the session this loop runs in. Either
the harvest supports impersonated reads, or this subsection is human-ratified and **must say
which**. A visibility claim that quietly rests on an admin read is confidently wrong.

## A chain someone can follow — mandatory on every process page

A process page must be **traversable**, not merely readable. Among the artifacts a page
cites, at least one must reference another artifact the brain has actually mapped — a
reference column, or a sys_id inside a script, condition or property value. That single
link is what turns a catalogue of records into an account of a mechanism.

**Why it is checked, and what it caught.** The persona section above was for a long time the
*only* completeness test on a process page, so the technical half — the half a developer
opens the page for — was entirely unpoliced. Measured on run 93838afe87:
`case-triage-and-routing.md` cited **eleven artifacts and carried zero followable links**,
and it is the routing chain, the most-cited mechanism in the build. The page reads well. An
agent asked *"what happens to a case after triage"* cannot traverse one step of it.

**What is demanded is a sentence, not a chain.** No page can invent a reference the instance
does not contain, so a page with no followable link satisfies this clause by **saying so**:

```markdown
<!-- slot: mechanism.chain | source: HV | status: unfilled | blocked_on: <what> -->
> The chain stops at <artifact>; where it goes next is not readable from what was harvested.
```

**Citing more artifacts is not an answer.** An unrelated citation that happens to resolve is
precisely the reading this clause exists to refuse. A page citing fewer than three artifacts
is owed nothing: no chain is possible, so none is required.

**Unfilled slots are emitted, never skipped**, here and everywhere else on the page:

```markdown
<!-- slot: personas.may_see | source: LB+IV | status: unfilled | blocked_on: Q-014 -->
> Not yet documented — blocked on Q-014.
```

Silent absence is indistinguishable from a claim that there was nothing to say, and it is
uncountable, so nobody can measure how far from done the page is.

## Size & splitting

- **Cap ≈ 5k tokens (~20KB) per page** — measured in tokens, not lines; enforced by the
  frontmatter checker. Story pages additionally target ≤150 lines.
- Design split axes up front, don't shard reactively. Example: a large process area →
  one page per subprocess + ONE lifecycle/state-machine page with a single named owner.
  Hub pages link only — no content of their own.
- Dense but complete. No strikethrough resurrection of superseded analyses — summarize
  the outcome and move on.

## Archive rules

- Legacy originals go to an archive directory **outside** the searched docs tree
  (e.g. `_archive/` at the repo root) — each prepended with
  `ARCHIVED <date> — superseded by wiki/<page>; do not use.`
- **Never cite archived content as current.** If an archived fact is still true, it must
  be (re)stated on its owning wiki page and cited from there.

## Ritual hooks (why the frontmatter matters)

Story-close is the one maintenance ritual; nothing is calendar-driven. Per close it
produces: story page + index line + process-page deltas (walking `affects:`) +
decision/TBD ledger entries + registry updates + agent-memory promote/sweep. Validators
run automatically; no page is correct unless the checker passes.
