# Glossary — controlled vocabulary

> Single source for project terminology. Use these terms exactly, everywhere.
>
> ⚠️ **Verify every term against its owning page before adding it here — an unverified
> day-one glossary is how a wrong expansion of a core acronym survives for months.**
> A glossary written from first impressions gets cited by every later document and
> becomes self-reinforcing: the error looks authoritative precisely because it is listed
> here. When a term smells off: check the owning wiki/process page (or ask the customer),
> fix it HERE first, then sweep the pages that cite it.

## Usage rules

- **Add a term on its first documented use** — next to the page that introduced it, with
  a link to the owning page. A term used twice without a glossary row is already
  drifting.
- **Never abbreviate outside this list.** If an abbreviation is not defined here, write
  it out in full; if you need it often, add it here first.
- **Domain terms stay in their native language.** Customer-domain words are names, not
  translatables — do not translate them in English pages, and record the native form as
  canonical.
- **One meaning per term.** If the business overloads a word, register both senses as
  separate rows with disambiguating context, and prefer the unambiguous synonym in docs.
- Platform terms (e.g. "configurable workspace", table/artifact names) get rows too when
  the project uses them in a constrained way — the Context column says what is and is
  not meant.
